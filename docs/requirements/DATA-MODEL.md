# First relational slice — P07
Site -> Router -> Backend (Hotspot / UM6 / UM7 / PPPoE), with one backend of each kind per router.
Backend -> Plan and Batch; Batch belongs to a Plan in the same backend. Voucher belongs to a Batch in the same backend. Composite alternate keys and foreign keys enforce namespace consistency. Usernames are unique per backend with exact case (BINARY); any case-normalization rules require RouterOS evidence. Plans and site names use local exact names; no assumption that router IDs equal local IDs. GUIDs are local immutable identifiers. Foreign-key deletes are restricted; archive policy later.
Voucher here is only a reservation record, not a credential, not a confirmed remote account, not printable. Backend kind is configuration, not detected capability. No remote command is issued. Validity, usage, sale, print and synchronization state, secure credentials, full audit, session and monitoring tables will be added at their planned gates. No status conflation or inferred success. P08 versioned migrations, WAL/transaction/recovery and backup verification; P09 credential protection; P10 audit/backup.

## P16c.1 — Local UM6 creation journal (schema v5)
Each local UM6 reservation may receive one immutable creation entry with backend/router/customer/username identity, no plaintext credential or remote payload. State 1 Prepared -> 2 DispatchStarted -> 3 Indeterminate OR 4 Acknowledged; atomic conditional transitions, no rearm, no deletion, no confirmed/printable state. Only a committed successful claim may authorize future dispatch; no network implementation or caller yet. A crash after claim must be treated as uncertain even if no bytes were sent. Acknowledgement alone is not evidence of correct account, password, profile assignment or activation. Current reservation identity is checked at transition; future dispatcher must revalidate target identity and enforce no concurrent edits across network operations. No secret storage or batch-generation logic yet.
Schema v4 upgrades transactionally on managed startup after identity/integrity checks. Verified v4 snapshots can upgrade on a staged copy; originals remain unchanged. Older snapshot versions remain unsupported. At P16c.1 managed restore activation initially blocked any current or candidate creation journal entries until safe cross-generation reconciliation could be implemented. See P16c.2 below for the revised guard. Direct file copying/rollback outside managed APIs and hostile local SQLite writers are not protected. Recursive triggers enabled for managed connections to prevent REPLACE bypass. This is a local safety foundation, not remote exactly-once delivery. Next: durable reconciliation/restore policy, verified target parameters and a one-shot UM6 create/activate adapter with explicit uncertain outcomes, no automatic mutation retries.

## P16c.2a — Conservative cross-generation reconciliation
Under the exclusive managed gate, prepare the authenticated candidate and verified precaution, then stream and compare both creation journals in reservation-ID order. Require exact equality of every creation entry and state plus its reservation/batch/plan/router/site relationship and current descriptive target names; reject inconsistent joins, missing, extra or different rows. Comparison is read-only and uses bounded row-at-a-time memory. Identical histories (including Indeterminate or Acknowledged) may restore without rearming. Older or divergent histories remain blocked; no union, automatic remote retry, deletion or inference of successful creation. A rejected candidate retains the precaution and old generation; new candidate may remain on disk. Future remote endpoint identity, credential verification, actor evidence, durable cross-generation conflict resolution and actual remote readback remain necessary. No remote dispatch implemented. Direct file rollback and uncooperative writers are outside the guarantee.

## P16c.2b — Local recovery review read model
Per-router read-only review of DispatchStarted, Indeterminate and Acknowledged entries; all still need verification and cannot be replayed or printed. Prepared remains separate. Keyset pagination by reservation ID (1–500 rows, fetch one extra only); local identity consistency flag via left joins, retain drifted rows for investigation. Counts are four disjoint local journal states, not remote account or session counts; a failed query is not a zero result. Page and counts are independent observations, not a common snapshot across calls; concurrent state changes can affect paging, restart from first page on refresh. No schema changes or new index; existing RouterId-leading uniqueness index used for router filtering, performance qualification remains P47. Read methods use existing read-only schema validation and never create/migrate a DB. No credentials, no automatic resend, no remote verification or reconciliation state mutation. A stable authenticated router endpoint binding and creation/activation command evidence are still required before remote readback or dispatch. The review counts are intended as real dashboard inputs in P41, not fabricated production data.

## P16c.3a — Bound creation intent (schema v7)
Attach an immutable intent to an existing prepared UM6 journal only after a matching enrolled router exists. Capture local batch/plan IDs and plan name, leaf certificate fingerprint, explicitly selected remote profile owner/name (no inference from local plan name). No password or remote command payload. Insert validates all relationships; update/delete/replace rejected by managed SQLite triggers. Bound one-shot claim compares current local relationships and pinned target in an immediate transaction. Legacy unbound local claim cannot claim a bound intent; legacy claims are not permission to send. No rearm and no remote success or printing inferred. Exact intent equality additionally required before managed restore activation; v4–v6 staged migrations and startup remain supported. No real remote write, profile verification, secret binding, concurrent configuration freeze, actor authorization or command qualification yet. These are required before a production dispatcher; local claim is only a prerequisite. The caller must use the managed session and no raw writers. 

## P16c.3b.1 — Protected voucher secret (schema v8)
Store one immutable encrypted password envelope per prepared bound intent; absent record and intentionally empty password are distinct. Reuse existing AES-256-GCM and Windows CurrentUser DPAPI key protection with the reservation GUID and disjoint um6-voucher-password/v1 purpose authenticated. No plaintext stored, no separate dependencies. Read validates envelope length before materialization, decrypts into disposable byte lease and clears owned bytes on disposal. Bound local claim must successfully decrypt inside its immediate transaction; absent secret returns false, corrupt/unavailable secret throws and rolls back the claim. Legacy unbound claim cannot claim an intent. No remote dispatch or printing authorization. Managed restore requires exact ciphertext records, in addition to prior journal/intent/target comparisons; no automatic re-encryption or substitution. Other Windows users/devices may be unable to decrypt; separate voucher recovery/portability policy, generation, text encoding rules, profile readback, concurrent configuration freeze, actor authorization and actual create/activate commands remain open. Existing schema v4–v7 startup/staged migration supported; no changes to remote subscribers. Same-user hostile writes and raw rollback remain outside protection.


## P16c.3c.2c — Durable creation evidence (schema v9)
An append-only evidence table separates kind 1 acknowledgement (optional returned opaque ID) from kind 2 exact disabled readback (required opaque ID). Acknowledgement state and receipt insert commit atomically; failure leaves DispatchStarted. Optional qualification readback occurs only after commit; absence or mismatches never remove the receipt, and no uncertain creation is replayed. Triggers require current matching bound intent, reservation, router target, retained secret and acknowledged journal; observed ID must match any returned ID. Existing state-only acknowledgements are not backfilled. No remote ID uniqueness claim beyond the exact readback observation, no new journal state, no credential proof, entitlement, activation or print eligibility. Managed restore requires exact evidence equality, including null returned ID, and schema v8 snapshots upgrade on a staged copy. Uncooperative local writers and raw rollback remain outside guarantees. Production connection binding, authorization, remote recovery and physical qualification remain open.
