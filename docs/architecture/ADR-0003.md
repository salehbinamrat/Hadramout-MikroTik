# ADR-0003 — Versioned SQLite and durability (P08)
A frozen SQL migration chain, independent of the changing EF model, is executed through the existing Microsoft.Data.Sqlite provider. No second ORM or production dependency. Schema v1 creates the six baseline entities; v2 adds composite FK lookup indexes. Both versions are internal initial development versions; no previously released v1 database is claimed. An immediate write transaction serializes initialization and upgrades. Application identity and schema version are checked before mutation; unknown populated databases, mismatched identity and future schemas are rejected. DDL and version changes commit atomically. SQLite WAL is selected after migration (outside the transaction), synchronous FULL on each owned connection, foreign keys on, no pooling, bounded command timeout. The caller owns the returned open connection.
DatabaseProbe uses a disposable file and migration chain; no user files. No production data path is selected yet. Legacy EnsureCreated test fixtures are confined to tests; no production creation through EnsureCreated. Future migrations append new steps, never edit an accepted step, add model/constraint regression evidence and pre-upgrade backup policy before real data migration. Do not copy a live WAL database file alone.
Tests cover new initialization, synthetic v1 upgrade, transactional DDL rollback, rejection of unknown/future databases, identity, concurrent initialization, rollback on disposal and real migrated constraints. No power-loss or hard-kill guarantee is claimed; physical crash/fault and disk-full tests and encrypted credential/backup policies remain pending. WAL requires a local supported filesystem; do not deploy on network shares.

## P11b — Certificate-authenticated TLS transport
Official references: https://help.mikrotik.com/docs/spaces/ROS/pages/47579160/API and https://learn.microsoft.com/dotnet/api/system.net.security.sslclientauthenticationoptions.certificatechainpolicy . Use .NET TcpClient/SslStream with TLS 1.2 or 1.3, required encryption, explicit expected DNS/IP certificate identity, port 8729 by default, no renegotiation and no insecure retry. Platform chain/name/validity/EKU checks are mandatory; no certificate acceptance callback. System trust uses online revocation checks. For isolated offline networks an explicitly pre-provisioned private CA (DER public certificate) may be configured, with CustomRootTrust and no revocation lookup; this deliberate offline mode requires administrator-controlled CA distribution, rotation and revocation outside the client. It does not trust a leaf or automatically accept a peer certificate. Disable automatic issuer downloads; the router must present necessary intermediates. Connection and handshake share one cancellation/deadline budget (15s default, 2min maximum); do not infer bounded DNS or OS chain-validation timing under every platform condition. Dispose failed transports. No credentials sent yet; subsequent command/read/write timeouts and response limits are separate.
Loopback TLS tests with synthetic CA/leaf check valid exchange, wrong host, untrusted root, expired leaf, system trust rejection, cancellation, silent peer, leaf-as-CA and input validation. No production certificate store modifications or real router access. RouterOS v6.49.x requires configured API-SSL with valid certificate and TLS 1.2 support; anonymous DH and plaintext API are intentionally unsupported. Actual RouterOS and Windows x86 physical-device interoperability remain unverified.

## P12a — Authenticated single-command sessions
Use the documented post-v6.43 /login exchange only after certificate-authenticated TLS. Require a bare !done for login; challenge, error, fatal or unknown replies fail closed, dispose and never expose a session. Caller-owned UTF-8/byte credentials stay stable until completion; temporary prefixed credential buffers are zeroed even on failed writes, no peer-provided text in exception messages. No legacy MD5 login or plaintext fallback. Shared connect/login deadline, command deadline, caller cancellation kept distinct. The first internal read-only command requests just the resource version, expects exactly one data reply with one bounded ASCII version field then bare completion. Unknown/error/empty/malformed replies, transport failures or cancellation after beginning a command close the session; no automatic resend. Concurrent commands are rejected instead of overlapping reads. This conservative initial command does not yet implement the general !re/!empty/!trap/!done response model or version/capability parsing. No mutation API or real router connection. Uses the same Schannel-compatible loopback fixture as PR #14. Tests include synthetic v6/v7 version strings, authentication failures, certificate mismatch, malformed version replies, session cancellation and deadline. Actual v6/v7 field checks, credential lease integration and endpoint persistence remain pending.

## P12b — Bounded common read reply semantics
Official RouterOS API reply model (https://help.mikrotik.com/docs/spaces/ROS/pages/47579160/API): !re data, !done completion, !trap rejection, !fatal termination, !empty introduced in v7.18. The shared read-only untagged reader exposes completed/rejected/fatal outcomes, with optional recognized numeric trap category 0–7, never raw peer error text. Completion requires !done; legacy empty !done and explicit !empty then !done are supported. Reject inconsistent empties, duplicate/invalid attribute names, unexpected tags and completion attributes, unrecognized reply types, and missing completion. Any trap/fatal immediately discards projected partial rows and requires closing the owning session rather than consuming a potentially pending !done as the next command's reply. A trap is not proof a mutation had no effect; no mutation API exists. Bound each frame via the existing codec plus aggregate 16 MiB payload, at most 4096 rows and maxRows+2 sentences; raw buffers are cleared. Projectors must select bounded values and not retain byte arrays or perform side effects. Version command now uses the common reader, still requires exactly one valid ASCII version row. This is an internal read-only subset, not arbitrary commands, tagged multiplexing, streaming all records or write/reconciliation support. Actual device behavior and large-table paging need further verification.

## P14a — Bounded read-only reconnect policy
A separate internal RouterOsReadRecovery facade exposes only version, discovery and service-probe reads. No arbitrary caller delegate or mutation is exposed. Entire operation including connect, login, read, optional 250 ms delay and one fresh authenticated connection shares one cancellation/deadline budget (15 s default, maximum 2 min). Retry at most once after an authenticated read fails with explicit EOF or socket ConnectionReset/ConnectionAborted/NetworkReset/Shutdown (direct or immediate IOException inner). Dispose first session before delay; repeat the entire read and do not return partial results. No retry for initial connection/login/TLS errors, generic IO, protocol invalidity, trap/fatal outcomes, timeout or caller cancellation; no trust downgrade or automatic mutation replay. Uses caller-owned credential/CA buffers, stable through completion, no new stored secrets. No persistent session pool, device-wide backoff, circuit breaker or background polling yet. Local deadline is cooperative with OS TLS/DNS operations. Field tests, larger table reads and explicit reconciliation for uncertain writes remain pending. Tests reuse the existing Schannel-compatible certificates and observe server tasks.

## P14b — Bounded read admission
The recovery facade now has a process-wide admission gate: maximum eight in-flight logical reads (initial conservative engineering default, not a measured throughput limit), maximum one per normalized host and port, no unbounded waiting queue. The lease covers connect, TLS, authentication, all read commands, retry delay and replacement connection; released in all terminal paths. DNS case, trailing dot, IDN and equivalent IP spellings are normalized; IPv4-mapped IPv6 maps to IPv4. Certificate identity/credentials are not admission keys; results are never shared or coalesced. Different DNS aliases, NAT endpoints and ports can still refer to the same physical device, and direct lower-level session calls bypass admission; future production scheduler must use the facade and stable configured router identity. Busy reasons distinguish endpoint contention and global capacity, not connection failure. No automatic requeue or per-router cooldown in this slice; UI/scheduler must avoid busy polling. Active set holds at most eight entries, idempotent lease disposal cannot release a subsequent operation. No new dependencies. Physical concurrent-load limits, adaptive backoff, future mutation coordination and field validation remain pending.
