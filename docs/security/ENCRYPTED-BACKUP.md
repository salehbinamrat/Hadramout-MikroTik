# P10b — Password-authenticated encrypted backups (v1)

Format: 8-byte magic HMKBACK1, 16-byte random salt, 12-byte random nonce, 4-byte little-endian plaintext length, ciphertext, 16-byte authentication tag. Derive 32-byte key via PBKDF2-HMAC-SHA256, fixed 600,000 iterations for v1; authenticate complete header as AES-256-GCM associated data. No dynamic algorithm or attacker-controlled KDF cost. Reject malformed lengths before allocation and authenticate before creating a plaintext restore snapshot. Receipt SHA-256 is for transfer verification; AEAD is the authentication mechanism. Password required 12–1024 UTF-8 bytes; UI must provide clear password guidance, confirmation and no logs. Callers own password buffers; derived key and plaintext arrays cleared in finally. No new packages.

Current single-message v1 explicitly limits SQLite snapshots to 64 MiB to bound memory use in x86. Larger databases require a reviewed streaming/chunked format before production capacity claims. Files created through non-overwriting moves. Raw SQLite snapshots exist transiently on trusted local storage in the source directory for export and candidate directory for restore; cleanup on normal/failure exit is implemented, but sudden termination can leave temporary files. Directory permissions, startup cleanup and full disk protection still required; deletion is not secure erasure. Do not use untrusted/shared directories. Existing raw snapshot API is internal workflow baseline, not recommended for external distribution. Only restore trusted backups; no active database is replaced.

Portable database content does not imply portable DPAPI router credentials. Encrypted backup password alone does not unlock router credentials on another Windows account/device. Explicit re-entry/reset or controlled rekey workflow is pending; no silent reset. Live activation, pre-activation safety snapshot and preservation of audit history are still pending. No production data used.
