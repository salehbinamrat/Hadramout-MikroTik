# P10 — Safe local snapshots and staged recovery (initial slice)

The SQLite online backup API captures committed data including WAL without copying only the main database file. The snapshot is staged in the destination directory, checkpointed to a standalone file, checked for application ID, exact current schema version, integrity, foreign keys and required tables, then published with a non-overwriting move. A SHA-256 receipt is returned; caller must retain it separately in a trusted location. A matching digest alone does not authenticate an attacker-controlled backup. Only trusted local backups are supported, not arbitrary imported SQLite files.

Restore requires a trusted SHA-256 receipt, copies and verifies exact bytes before SQLite opens them, validates snapshot and prepares a new database candidate. No active database replacement, no deletion, no merge with current live history and no automatic activation. Snapshot and candidate events are appended to their own databases, not the source; successful credential saves/removals are recorded atomically with their changes. Audit events allow only typed operation, UTC time, UUID and optional router UUID; no arbitrary payload. Triggers prevent ordinary SQL UPDATE/DELETE; this is not tamper-proof against a privileged database editor. Actor attribution, all future operations, failures, live restore activation, preservation/merge of current audit history and mandatory pre-activation backup need design before enabling UI restoration. No claim of full P10 completion.

Credentials remain DPAPI CurrentUser encrypted, never exported as plaintext. Same Windows account/profile and machine recovery tested in hosted CI when checks pass; cross-device/account recovery requires re-entry or an explicitly designed rekey workflow. Backups currently contain non-credential data in ordinary SQLite form; not suitable for untrusted storage; authenticated whole-backup encryption, retention and scheduling remain pending. No live database or real secrets used. No power-loss/hostile-file safety claims. Keep on a trusted local filesystem.

## P10e — Protected recovery preparation
PrepareWithPrecaution authenticates and validates the incoming backup in an isolated candidate first. It snapshots the current DB once, encrypts and independently authenticates that same snapshot as a non-overwriting precaution, then streams its original audit rows into the staged candidate in one transaction. Identical event IDs are deduplicated only when timestamps, kind and subject match exactly. Conflicting IDs fail closed and the already verified safety copy remains available. The returned SHA-256 receipts describe the published files before any future opens or edits. Current database and incoming backup are not replaced; candidate published only after integrity, FK and identity checks. Existing snapshot publication helper now also serves encrypted output; path and collision checks are shared instead of duplicated.
The current history is preserved through the precaution snapshot instant only. Caller must quiesce all writers and revalidate before any actual activation; no activation, production path, user permissions, retention or scheduled deletion implemented. Both workspace parents must be private trusted local storage; crash recovery and ACL enforcement remain separate work. No actor identity yet; future RBAC must gate actual restore. The safety copy uses a caller-supplied independent password; no password is logged or persisted. No real data used.

## P10f — Private temporary workspaces
All raw SQLite staging, encrypted output staging and decrypted candidates now use the same helper. On Windows an explicit protected DACL with only the current user, owner and inheritable full control is supplied at creation and verified before plaintext is written; reject unexpected ACLs or reparse points. Non-Windows local test environments require 0700. No permissive fallback, no new dependency. Existing paths are not swept or deleted. Random temporary workspaces are removed by existing finally scopes; their restrictive permissions persist if a process is terminated before cleanup. These measures do not encrypt temporary plaintext on disk, protect against same-user malware/privileged administrators, guarantee secure deletion, or make untrusted parents safe. Windows backup/restore must use ACL-capable trusted local storage; published encrypted files can inherit restrictive ACLs when moved. Recovery of abandoned workspaces and managed application storage/lifecycle policy remain pending. No automated deletion of unknown directories.

## P10g — Managed generation activation foundation
Use a trusted, private, local Windows directory. ManagedDatabase.OpenSession acquires a non-shared file gate for the complete application session; every DB connection and background operation must finish before disposal. ActivateRestore requires the same exclusive gate, no open managed session, and explicit expected generation. It authenticates the selected backup, creates a fresh verified precaution, merges current audit history, verifies candidate digest and credential availability, and atomically replaces only the small active-generation pointer using File.Replace on supported local Windows filesystems. Old database generations are retained; never overwrite, delete or rename them. Invalid/missing pointers fail closed if an existing generation is present. Unavailable router credentials require explicit consent; actual login remains untested. On failure after candidate publication, retain that candidate for explicit recovery, never delete it automatically. No new dependencies.
This is a cooperative lifecycle API foundation, not connected to the WPF production startup or future role permissions yet. All live access must use the gate; it cannot stop external SQLite writers or a caller that ignores the session contract. Local managed root creation/ACL policy, UI/RBAC, cross-device field testing, power loss, orphan reconciliation and explicit retention remain pending. No production DB changed. Do not use network/shared directories or an untrusted root. 

## P10h — Application startup integration
Normal desktop launch uses Windows LocalApplicationData/HadramoutMikroTik.Data, independent of x86/x64 and installer/portable executable location. This is intentionally a shared per-Windows-user data root rather than an executable-relative portable data store. Require local fixed drive, no reparse-point ancestor, explicit current-user-only protected directory ACL on create, and exact ACL verification on subsequent opens; reject broad existing permissions rather than silently altering data. All normal WPF runtime holds the managed session until application exit. Startup checks identity, opens existing DB for SQLite recovery, checks quick_check, foreign keys and required tables; no silent reset or deletion. Smoke tests use temporary private data only and exercise reopen. Full backup integrity checks unchanged. Future data services must operate under the held session; restore UI, RBAC, lifecycle of async jobs, deliberate managed cleanup and real power-loss testing remain pending. This is not whole-database encryption or protection from privileged/same-user actors. The active application root is not an installer deletion target.
